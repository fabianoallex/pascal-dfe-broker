# pascal-dfe-broker — contexto do projeto

Ferramenta open source para consulta e distribuição de Documentos Fiscais Eletrônicos brasileiros (NFe na v1; CTe, MDFe e demais DFe planejados, idealmente via contribuição de terceiros) via serviço de **Distribuição de DFe** da SEFAZ. Usa componentes **ACBr** (LGPLv3) para a comunicação fiscal e o broker AMQP embutido do projeto-irmão `../pascal-amqp-faa` (MIT, mesmo autor) para distribuir os documentos como mensagens em filas configuráveis pelo usuário. MIT.

**Estado em 2026-09-18: 68 testes cobrindo tudo que é puro/testável sem ACBr nem broker, confirmados nos dois compiladores.** FPC via `lazbuild` e Delphi via a IDE (`PascalDfeBroker.groupproj`) — **68/68 nos dois**, 0 falhas, 0 erros, 0 vazamento de memória. A compilação real (não só leitura) já pegou defeitos reais que só apareceram assim (ver "Gotchas dual-compiler"), incluindo dois vazamentos de memória reais medidos por heaptrc — um de um padrão de teste comum (objeto construído inline como argumento de chamada que levanta exceção), outro de um erro simples meu (fixture criado no `Setup` mas usado só por parte dos testes). Existem interfaces completas (`DFe.Types`, `DFe.Provider`, `DFe.Errors`, `DFe.Publicador`) e implementações reais e testadas de verdade de tudo que independe de ACBr/broker: `DFe.RoutingKey`, `DFe.CursorStore.Arquivo`, `TDFeProviderRegistry`, `DFe.Orquestrador`, `DFe.Host.Loop`, `DFe.Config` (`CarregarConfig`/`RecarregarConfig`/`TDFeConfigWatcher`) e `DFe.Manifestacao` (manifestação do destinatário automática e manual — ver decisão 14) — via dublês de teste em `DFe.TestDoubles.pas`, incluindo um relógio controlável para `TDFeOrquestrador`, um `Esperar` no-op para `TDFeHostLoop`, uma fábrica fake de client, uma data de modificação controlável para `TDFeConfigWatcher`, um provider fake que também implementa `IDFeManifestador` e uma fonte de comando fake para `DFe.Manifestacao`. Nenhum teste depende de `Sleep`/tempo real, ACBr ou certificado. O que falta está em "Próximos marcos" no final deste arquivo.

**Grupo de projeto Delphi na raiz: `PascalDfeBroker.groupproj`** (criado pelo usuário em 2026-09-18, mesmo papel do `AMQP.groupproj` do `pascal-amqp-faa`). **Todo novo projeto Delphi (`.dproj`) deve ser adicionado a esse grupo** — é o que permite compilar tudo de uma vez pela IDE nesta máquina. Hoje só tem `tests\Unit\DFe.UnitTests.dproj`; os hosts (console, serviço Windows) entram aqui quando forem escritos.

**Nota sobre `tests\Unit\DFe.UnitTests.dproj`**: a IDE reescreveu esse arquivo ao abrir (expandiu para a matriz completa de plataformas que o Delphi 23 gerencia por padrão — Android/iOS/OSX/etc. — em vez da versão enxuta Win32/Win64 que foi escrita à mão nesta sessão). Isso é comportamento normal da IDE, não um erro; a versão no disco é a que compila e passa os testes, então é ela quem vale.

## Decisões travadas

1. **Escopo v1 = NFe apenas.** CTe/MDFe vêm depois, com preferência explícita por virem de contribuição de terceiros — por isso o contrato de provider (`docs/architecture.md`) e o `CONTRIBUTING.md` existem antes de haver qualquer provider implementado: a uniformidade entre tipos de documento é requisito de design, não polimento posterior.
2. **Dual-compiler Delphi + FPC/Lazarus desde o início**, mesmo padrão do `pascal-amqp-faa` (`{$I ...inc}`, `MODE DELPHI` no FPC). Motivo do autor: pretende eventualmente usar o projeto com Lazarus em algo próprio, mas sem comprometer funcionalidade por causa disso — onde o ACBr for uma limitação real em Lazarus, documentar o limite, não forçar.
3. **Broker AMQP embutido** (reusa o submódulo server do `pascal-amqp-faa`, que já roda dentro do processo hospedeiro sem exigir infraestrutura externa), com compatibilidade para apontar a um AMQP externo (RabbitMQ etc.) por falar o protocolo 0-9-1 padrão.
4. **Convenção de routing-key fixada**: `<tipo>.<categoria>.<uf>.<cnpj>` numa exchange topic única `dfe` (ver `docs/architecture.md`). É a interface pública mais importante do projeto — não muda por decisão de PR isolado depois de haver consumidores reais.
5. **Licenciamento**: MIT neste repositório; ACBr como dependência LGPLv3, integração preservando a separação (sem incorporar código ACBr sob a licença MIT deste repo).
6. **Integração com ACBr via componentes clássicos** (`TACBrNFe`/`TACBrCTe`/`TACBrMDFe`, compilados direto no binário, sem DLL/`.so`) — **revertido de ACBrLib em 2026-09-18**. Motivo: a ACBrLib tem fonte LGPL livre, mas o binário pré-compilado oficial exige assinatura paga "ACBr Pro"; a versão DEMO gratuita só emite em homologação e expira a cada 30min de uso — inviável em produção sem pagar ou compilar a lib você mesmo. Componentes clássicos são só código-fonte (mesma licença LGPL) compilado direto no projeto — não existe binário de terceiro pra vender, então essa fricção desaparece. Expõem `ConsultarDistribuicaoDFe` (por último NSU, NSU específico ou chave) + `DescompactarXMLZip` para o `docZip`, mesmo dado que a ACBrLib devolvia. Trade-off aceito (o inverso do que valia antes): superfície de dependência maior (componentes também fazem emissão, DANFE, etc.) e maturidade prática em Lazarus/FPC para Distribuição de DFe ainda não testada por nós. Ver `docs/architecture.md`, "Integração com ACBr — decidido: componentes clássicos (revertido de ACBrLib)", para as fontes e a decisão original.
7. **Regras de Distribuição de DFe verificadas contra as NTs oficiais** (não mais suposição): intervalo mínimo 1h sem escalonamento de backoff; código de cStat de consumo indevido NÃO é universal (656 NFe/CT-e, 678 MDF-e) — ver `docs/referencias/README.md`.
8. **Cursor de NSU persistido em arquivo próprio** (`src/DFe.CursorStore.Arquivo.pas`, `TDFeCursorStoreArquivo`) — texto plano `namespace=nsu`, sem cache em memória (sempre lê/escreve o arquivo inteiro; volume é irrisório), escrita sempre via arquivo temporário + substituição atômica. SQLite e reuso do WAL do `pascal-amqp-faa` foram avaliados e rejeitados por desproporção — ver `docs/architecture.md`, "Persistência do cursor de NSU", para a justificativa completa. **Não é thread-safe para escritas concorrentes** — assume o orquestrador sequencial atual.
9. **Formato de entrega: mais de um host fino, mesmo core.** Console (dual-compiler, Windows/Linux — no Linux **é** o host de produção, rodado sob systemd, sem daemonização própria) + Serviço Windows (Delphi/VCL `TService`, Delphi-only de propósito — Serviço Windows é uma noção inerentemente Windows). Ambos usam `TDFeHostLoop` (`src/DFe.Host.Loop.pas`) para a cadência de tick (60s padrão, configurável) sobre `TDFeOrquestrador.ExecutarCiclo`. Consequência: `ExecutarCiclo` agora isola cada unidade de trabalho num `try/except` (uma unidade com bug não derruba as demais nem o processo). Os `.dpr`/`.lpr` dos hosts em si ainda não existem (dependem da integração ACBrLib real). Ver `docs/architecture.md`, "Modelo de execução".
10. **Auto-registro de provider via `initialization` de unit** (`TDFeProviderRegistry` em `DFe.Provider.pas`) — preferido a registro explícito numa config central porque essa alternativa exigiria o core conhecendo cada tipo de documento de antemão, o oposto do que o projeto quer para contribuição de terceiros. `Registrar` levanta exceção em colisão de `Identificador`. Ver o snippet exato em `CONTRIBUTING.md`.
11. **Estrutura de projeto: pacote Lazarus (`packages/pascal_dfe_broker.lpk`), sem pacote Delphi** (mesma assimetria do `pascal-amqp-faa`: Delphi resolve via Search Path direto em `src/`, não precisa de um `.dpk` pra isso). **Framework de teste: dual DUnitX + FPCUnit espelhados**, mesmo padrão do `pascal-amqp-faa` — `tests/Unit/*.pas` (DUnitX) e `tests/Unit/fpc/*.pas` (FPCUnit), 52 testes cobrindo tudo que é puro/testável sem ACBr nem broker. Ver `docs/architecture.md`, "Estrutura de projeto/pacote e framework de teste".
12. **Formato de configuração: INI** (`src/DFe.Config.pas`) — mesma filosofia de `DFe.CursorStore.Arquivo` (texto plano, sem dependência externa; JSON/YAML descartados por falta de API comum entre Delphi/FPC ou de suporte nativo). `[dfe]` para intervalo/tick/cursor path; `[certificado:<alias>]` por certificado, com `Ativo` (default true). Campos de certificado digital "de verdade" (`.pfx`, senha) ficam fora de propósito — pertencem à implementação real de `IDFeDistribuicaoClient`. `RecarregarConfig` recebe uma fábrica de client injetada (`TDFeClientFactory`, `of object`) em vez de falar com ACBrLib diretamente — mantém `DFe.Config` testável sem ACBr nenhuma.
13. **Mais de um certificado, inclusive do mesmo CNPJ (troca antes do vencimento) — suportado.** O NSU pertence ao CNPJ/UF, não ao certificado, então dois certificados do mesmo CNPJ já compartilham o cursor sem duplicar/perder documento. Mas nunca podem estar `Ativo=true` ao mesmo tempo (risco real de consumo indevido, SEFAZ limita por CNPJ não por certificado) — `CarregarConfig` recusa a config se isso acontecer. Ativação é **manual via `Ativo`**, não detecção automática de vencimento (exigiria ACBrLib real, que não está instalada). **`RecarregarConfig`** substituiu `MontarUnidades`: reconcilia a config com um `TDFeOrquestrador` **já em execução** (alias novo cria unidade; alias existente só sincroniza `Pausada`, nunca recria; alias removido é pausado, nunca destruído) — mesma função serve carga inicial e recarga a quente. **`TDFeConfigWatcher`** detecta mudança no arquivo (data de modificação) e chama `RecarregarConfig` sozinho; o host liga isso ao **tick do `TDFeHostLoop`** (que já é virtual) em vez de um mecanismo de sinalização novo. Ver `docs/architecture.md`, "Mais de um certificado..." e "Recarregar sem reiniciar...".
14. **Manifestação do destinatário: configurável por certificado (automática ou manual), comando simples em vez de RPC clássico** (`src/DFe.Manifestacao.pas`). `TDFeOrquestrador` ganha um hook opcional `AoPublicarDocumento` (nil por padrão) chamado após publicar com sucesso um evento de categoria documento — o orquestrador não sabe o que é "manifestação", só avisa que publicou. `IDFeManifestador` é uma capacidade *opcional* de provider (verificada via `Supports` em runtime), simétrica a `IDFeDistribuicaoClient`/`IDFeProvider`. `TDFeManifestacaoProcessador` resolve o alias na unidade do orquestrador, envia o evento e publica o resultado como evento normal na mesma exchange (mesma `MontarRoutingKey`) — decidido não usar RPC clássico (reply-to/correlation-id) porque o broker já é pub/sub e quem manda o comando já está ouvindo a exchange. `IDFeComandoFonte` abstrai de onde vem o comando manual (fila AMQP, ainda não escrita). `TDFeAutoManifestador` liga o hook do orquestrador ao processador quando `TDFeUnidadeTrabalho.ManifestacaoAutomatica = True` (novo campo, também em `TDFeConfigCertificado`/`ManifestacaoAutomatica=` no INI, default `false`, sincronizado em `CarregarConfig`/`RecarregarConfig`) — resolve o caso de múltiplos CNPJ com políticas diferentes (um automático, outro manual) sem exigir nada além de um Boolean por alias, já que automático e manual convergem no mesmo processador. Ver `docs/architecture.md`, "Manifestação do destinatário".

15. **Fonte do ACBr: submodule git do mirror não oficial, com clone parcial + sparse-checkout** (`vendor/ACBr` → `https://github.com/MirrorProjetoACBr/ACBr.git`). O repositório oficial do Projeto ACBr é SVN, então não dá pra usar como submodule git diretamente; `MirrorProjetoACBr/ACBr` é sincronizado automaticamente via `git-svn` (cada commit carrega um trailer `git-svn-id` apontando pra revisão exata do SVN) e está ativo — commits de todo dia. Repositório inteiro tem ~1,3 GB (é o monorepo do ACBr inteiro: SAT, ECF, boletos, dezenas de provedores de NFSe, demos Android/iOS/React...); o `sparse-checkout` (modo cone) restringe o checkout a `Fontes/ACBrDFe`, `Fontes/ACBrComum`, `Fontes/ACBrOpenSSL` e `Fontes/Terceiros` (~70 MB), e o clone parcial (`--filter=blob:none`) evita baixar os blobs de fora desse escopo. **Não instalamos os componentes na IDE** — o broker só instancia `TACBrNFe`/`TACBrCTe`/`TACBrMDFe` em código (nunca arrasta pra tela), então basta as units estarem no search path do projeto; isso também é o que permite branches diferentes do broker apontarem pra revisões diferentes do ACBr sem conflito (instalação na IDE seria estado global da máquina). Escopo do sparse-checkout ainda **não é o mínimo exato** — só vai ficar claro quando a implementação real de `IDFeDistribuicaoClient` começar e o compilador reclamar de unit faltando.
    - **Rodar `./tools/init-acbr-submodule.sh` uma vez por clone** (idempotente) — faz o `git submodule update --init --filter=blob:none --depth 1` seguido do `sparse-checkout set`. `git submodule update --init` sozinho, sem o script, baixaria o repositório inteiro.
    - **Pinado em**: commit `578954903fdbe5c8ca57fe1a35b79c6c49e1ec79` (SVN `trunk2@48289`, 2026-09-17) — atualizar exige `cd vendor/ACBr && git fetch --depth 1 origin master && git checkout FETCH_HEAD` (ou refazer o script), commitar o novo ponteiro de gitlink, e documentar a nova revisão aqui.

Com isso, todas as decisões que ficaram em aberto ao longo da concepção e da estruturação inicial estão fechadas.

## Gotchas dual-compiler já encontrados

- **`SysUtils.RenameFile` NÃO se comporta igual nos dois compiladores/plataformas.** No Windows (Delphi e FPC), falha em vez de sobrescrever um destino já existente — diferente do `rename()` POSIX. Para substituição atômica de arquivo no Windows, usar `MoveFileEx` com `MOVEFILE_REPLACE_EXISTING` (unit `Windows`, sob `{$IFDEF DFE_WINDOWS}`) — `RenameFile` sozinho não serve para o padrão "grava em .tmp, substitui atômico" que `TDFeCursorStoreArquivo` depende. No Unix, `RenameFile` é o `rename()` POSIX de verdade e já substitui atomicamente.
- **`MOVEFILE_WRITE_THROUGH` não existe na unit `Windows` do FPC 3.2.2** (erro de compilação real, achado em 2026-09-18) — só `MOVEFILE_REPLACE_EXISTING` está declarada. Não era essencial pra garantia que importa (substituição atômica de conteúdo, não fsync de hardware), então foi removida em vez de contornada.
- **Nunca usar `Move`/`CopyMemory` sobre um array de interfaces (ou qualquer tipo gerenciado)** — copia os bytes sem incrementar refcount, deixando as duas cópias com contagem errada (destruição prematura). Copiar elemento a elemento (ver `TDFeProviderRegistry.Todos`).
- **`lazbuild` exige o `.lpk` registrado antes do primeiro build** (`Error: Broken dependency`) — rodar `lazbuild --add-package-link packages\pascal_dfe_broker.lpk` uma vez resolve; depois disso builds normais funcionam.
- **`packages/pascal_dfe_broker.pas` é gerado pelo Lazarus na primeira compilação do `.lpk`** (container que só lista as units do pacote) — é versionado no git, igual ao `pascal_amqp_faa.pas` do projeto-base, porque o `.lpk` depende dele existir pra compilar sem reabrir a IDE.
- **Um objeto construído inline como argumento de interface, numa chamada que levanta exceção, pode vazar no FPC 3.2.2.** Medido com heaptrc: `Registrar(TDFeProviderFake.Create(...))` vaza 1 bloco quando `Registrar` levanta (identificador duplicado) — a interface temporária criada pela conversão implícita classe→interface no ponto de chamada não é liberada corretamente no unwind de exceção nessa versão do FPC. Fix: atribuir a uma variável local de tipo interface *antes* de passar para a chamada (finalização de variável gerenciada é segura em unwind; argumento-temporário não é, nesse caso). Aplicado nos dois lados (`DFe.ProviderRegistryTests.pas`) mesmo sem confirmar se o Delphi tem o mesmo problema — o padrão é seguro nos dois de qualquer forma.
- **`TCustomIniFile.ReadBool` do Delphi NÃO entende o texto "true"/"false"** (achado pelo usuário rodando o Delphi real, 2026-09-18) — delega para `ReadInteger`/`StrToIntDef`, que só entende número; `"Ativo=false"` virava silenciosamente o *default* passado a `ReadBool` (`True`) em vez de `False`. **O FPC interpreta o texto direto e não tem esse problema** — os 52 testes passaram de primeira no FPC e esconderam o bug até rodar no Delphi de verdade. Fix: `DFe.Config.LerBooleano` interpreta a string na mão (`SameText(s, 'true') or (s = '1')`), sem depender de `ReadBool`/`ReadInteger` de nenhum dos dois compiladores. **Este é o gotcha mais sério até agora**: os outros foram achados pelo compilador que falhou; este só apareceu porque o *outro* compilador (Delphi) discordou silenciosamente do FPC — reforça que os dois lados precisam rodar antes de confiar em qualquer coisa nova.
- **Cuidado com fixture criado no `Setup`/`SetUp` mas usado só por parte dos testes de uma fixture.** Um objeto `TInterfacedObject` atribuído a um campo de teste com tipo de classe (não de interface) fica com refcount 0 até algo tomar uma referência de interface dele — se nem todo teste da classe faz isso, o heaptrc acusa vazamento nos que não fazem (medido em `DFe.HostLoopTests`: `FCursorStore` criado no `Setup` mas usado só por um dos três testes). Fix: só criar o fixture dentro do teste que realmente precisa dele.
